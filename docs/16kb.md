# 16 KB page alignment

Builds apply `io.github.supermonster003.autojs6-native-alignment:1.9.0`. Every assembled APK
is checked and reports are written to `app/build/reports/native-alignment/`.
Use `:app:verifyNativePageAlignment` to recheck existing artifacts.

Every language flavor produces APKs for `arm64-v8a`, `armeabi-v7a`, `x86`, and
`x86_64`, plus a universal APK containing all four ABIs. Keep the app's ABI
filters, ABI splits, and plugin service's `SUPPORTED_ABIS` declaration in sync.
ONNX Runtime and OpenCV provide the inference and image-processing libraries;
the runtime module supplies `libc++_shared.so` for each ABI from NDK
`28.2.13676358`. Its `src/main/jniLibs/libc++_shared.provenance.json` records
the source, SHA-256, and measured ELF alignment of each runtime library.

The gate enforces ELF PT_LOAD alignment for arm64-v8a and x86_64. Uncompressed `.so` entries also require 16 KB ZIP alignment. Third-party 32-bit alignment is advisory.

Every native dependency or toolchain upgrade must pass the gate again. Static alignment
does not prove runtime behavior: test on a device reporting `getconf PAGE_SIZE = 16384`
with compatibility mode disabled. No `android:pageSizeCompat` override is permitted.

中文: 构建门禁检查全部产物并输出 JSON 报告. 原生依赖或工具链升级后必须重新校验,
且需在页大小为 16384 的设备上关闭兼容模式后执行运行时验证.

[Deployment and device acceptance matrix](https://github.com/SuperMonster003/AutoJs6/blob/master/docs/dev/page-size-16kb-roadmap.md)

## Native inventory

`tools/16kb/check_elf_alignment.py` reports the PT_LOAD alignment of every `.so` in AARs,
APKs or directories and fails on a 64-bit library below 16 KB. Measured on 2026-10-30 from
the ONNX Runtime AAR in the Gradle cache, `libs/org-opencv-4_8_0/opencv-4.8.0.aar` and the
runtime module's `libc++_shared.so` (largest PT_LOAD alignment; 32-bit values are advisory):

| Library | arm64-v8a | armeabi-v7a | x86 | x86_64 |
|---|---|---|---|---|
| `libonnxruntime.so` (ONNX Runtime 1.21.1) | 0x4000 | 0x4000 | 0x4000 | 0x4000 |
| `libonnxruntime4j_jni.so` (ONNX Runtime 1.21.1) | 0x4000 | 0x1000 | 0x1000 | 0x4000 |
| `libopencv_java4.so` (OpenCV 4.8.0, rebuilt) | 0x4000 | 0x4000 | 0x4000 | 0x4000 |
| `libc++_shared.so` (NDK 28.2.13676358) | 0x4000 | 0x1000 | 0x1000 | 0x4000 |

```
python -I tools/16kb/check_elf_alignment.py <onnxruntime-android-1.21.1.aar> libs/org-opencv-4_8_0/opencv-4.8.0.aar libs/ppocrv3-plugin-runtime/src/main/jniLibs
```

ONNX Runtime comes from Maven Central (`com.microsoft.onnxruntime:onnxruntime-android:1.21.1`),
the same version as the Rapid OCR plugin, so packaged AutoJs6 apps that bundle both plugins
carry one `libonnxruntime.so`. Upgrading it changes this plugin, the Rapid OCR plugin and the
host's embedded engine together.

OpenCV runtime: the plugin uses the org.opencv Java API in its own process only, so its OpenCV
is a private detail that no other plugin or host build shares. `libs/org-opencv-4_8_0/opencv-4.8.0.aar`
keeps the vendor OpenCV 4.8.0 Java classes and resources; its four `libopencv_java4.so` entries are
rebuilt from the upstream 4.8.0 source (commit f9a59f2592993d3dcc080e495f4f5e02dd8ec7ef) with NDK r28c
and 16 KB ELF segment alignment. `opencv-4.8.0.provenance.json` records the upstream tag, the build
options and the per-ABI hashes, build IDs, NDK idents and alignments. Rebuild with
`tools/opencv/build_opencv_java.ps1`, check the AAR with `python tools/opencv/opencv_java_aar.py check`,
and verify the plugin on devices afterwards.
